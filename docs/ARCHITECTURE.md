# Architecture

## Stack and boundaries
React + TypeScript + Vite, strict mode, Vitest. Client-only MVP; no auth or remote AI API. Online multiplayer and anonymous analytics are optional server features (see MULTIPLAYER_PLAN.md and "Analytics" below); single-player still works fully offline. Three AI opponents run in the browser. LocalStorage save/load may be added after core gameplay.

```text
React UI -> turn orchestrator -> pure TypeScript game engine -> board/rules/card data
                  |                         ^
                  v                         |
             AI strategy -> legal-action interface
                            |
                            v
                     typed state + event log
```

The engine and AI must not import React, DOM, localStorage, or networking. Persistence is an adapter outside the engine. AI receives a player-specific view plus the legal actions generated by the engine; it must not inspect hidden/private state or directly mutate game state.

## Shared game screen
Single-player (`App.tsx`) and online play (`MultiplayerLobby.tsx`) both render the in-game UI through one component, `GameScreen.tsx`, so the two modes always look and behave the same. `GameScreen` is presentational: it receives the `GameState`, the viewer's seat id, a `GameActions` object and an event feed, and never mutates state. Single-player implements `GameActions` with local engine calls; online play implements them as server requests. `Constitution.tsx`, `BoardView.tsx`, `EventLog.tsx`, `PropertyModal.tsx`, `sound.ts` and `useEventFeed.ts` are shared the same way. Any new in-game UI belongs in `GameScreen`, not in either container.

## Analytics
- `src/game/stats.ts` — counters the engine records as play happens (optional on `GameState`, so older saved rooms still load).
- `src/game/analytics.ts` — `summarizeGame` (anonymous per-game summary) and `aggregateSummaries` (win rates with Wilson intervals, length distribution, money flow, bankruptcy causes, space and card stats, wealth curve). Pure; no browser or server imports.
- `src/game/analyticsValidation.ts` — validates untrusted summaries and rebuilds them from known fields.
- `src/server/analyticsStore.ts` + `api/analytics.ts` — Postgres table `analytics_games`; `POST /api/analytics/games/start|progress|finish` (single-player only; `progress` sends only the round number every 5 rounds so drop-off can be measured) and `GET /api/analytics/summary` (admin token).
- `src/app/telemetry.ts` — client reporting; silent on failure, skipped on Do Not Track. `src/app/AnalyticsDashboard.tsx` — admin dashboard at `#/analytics` (players: games, completion, abandonment, session length, office chosen, room sizes, drop-off by round, start hour, daily activity; gameplay: win rates, wealth curve, money flow, bankruptcy causes, property decisions, space profitability and traffic; every chart has a table view; `src/app/analyticsCharts.tsx`). Table `analytics_games` gains `last_round` and `last_seen_at`, added automatically with `ALTER TABLE ... IF NOT EXISTS`. A single-player game with no report for 60 minutes counts as abandoned; an online room counts as abandoned once it would have expired (12 hours).
- Balance reports: `npm run analytics:report` (`GAMES`, `SEED_BASE` optional) simulates seeded all-AI games and writes `reports/balance-report.{md,json}` (git-ignored). The simulation does not run in `npm test`.
- Environment: `DATABASE_URL` (shared with multiplayer) and `ANALYTICS_ADMIN_TOKEN` (required to read results; without it the summary endpoint returns 503).

## Domain model
Player: stable ID, name, role, controller (human/AI), AI personality/config if applicable, integer cash, board position, active/bankrupt state, jail/skip state, GO count, owned property IDs, turn metadata.

Property: stable ID/space ID, type (land/railroad/utility), purchase price, base rent/charge formula, owner or cooperative marker, leaseholder/expiry, mortgage state, development level, color group.

Game state: schema version, phase (setup/awaiting-roll/resolving/awaiting-action/debt-resolution/game-over), players, active index, board/property state, public/cooperative ledgers, draw/discard piles, structured event log, victory result.

AI decision interface: given a sanitized player view, legal action list, and injected random source, return exactly one legal action plus a short user-facing rationale. Validate returned action in engine. If strategy fails or returns invalid action, choose a deterministic safe fallback from legal actions. Limit each decision to one action; no recursive decision loops.

## Proposed engine API
- createNewGame(config, randomSource)
- rollForCurrentPlayer(state, randomSource)
- resolveLanding(state)
- getLegalActions(state, playerId)
- buyProperty(state, playerId, propertyId)
- leaseProperty(state, playerId, propertyId)
- endTurn(state)
- resolveDebt(state, playerId, action)
- developProperty(state, playerId, propertyId, targetLevel)
- mortgageProperty(state, playerId, propertyId)
- checkVictory(state)

Each action validates phase, actor, ownership, and affordability; computes before committing; applies atomically; returns typed state/events or a clear error. Failed actions leave state unchanged.

## Invariants
- Exactly four seats; one human controller and three AI controllers.
- Roles across all seats: one Politician, three Citizens.
- Currency is integer taka and cash never negative.
- Every transfer names source/destination.
- Public and cooperative funds are distinct.
- Ownership and leaseholder are distinct; no double rent payout.
- Cooperative property is tracked separately from individual owners and never double counted.
- Victory: the game ends when exactly one player is not bankrupt; `winner` holds that player's id.
- Bankrupt players do not take normal turns.
- Game-over state is terminal.
- AI can select only from engine-generated legal actions and receives no hidden-state access.
- Production randomness is wrapped behind an injectable RandomSource; tests are deterministic.
- Stored saves are versioned and validated (`src/game/save.ts`, `src/app/saveStorage.ts`, RD-131).
- Server abuse controls: `src/server/rateLimit.ts` (Postgres fixed-window limiter, fails open), `src/server/cleanup.ts` and `api/maintenance.ts` (daily cron, `CRON_SECRET`; optional `RATE_LIMIT_SALT`), absence handling in `src/server/roomTick.ts` (RD-130, RD-132).
